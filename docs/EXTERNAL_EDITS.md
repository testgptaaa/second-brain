# Внешние правки и конфликты

Статус: подтверждено, что человек может просматривать и редактировать файлы памяти сторонними программами. Ниже — технический контракт подхвата изменений, ревизий и конфликтов. Реализация не начата; конкретная библиотека наблюдателя и числовые задержки требуют проверки на Mac и Windows в E02.

## Границы

- Markdown, JSON и вложения — источник истины долговременной памяти; SQLite — производный индекс и служебное состояние.
- Приложение не перезаписывает пользовательский текст молча. Внешняя правка — обычное изменение, а не ошибка.
- Совместное редактирование одного файла двумя программами в реальном времени не поддерживается. Приложение фиксирует расхождение и сохраняет обе версии.
- Внешний файл считается недоверенным вводом: YAML, Markdown и ссылки проверяются, путь не выходит за корень памяти.

## Обнаружение изменений

Наблюдатель файлов получает события, а сверка хешей проверяет пропущенное:

- при запуске приложения;
- после возвращения из сна или восстановления доступа к папке;
- периодически, предлагается раз в 5 минут;
- перед любой записью приложения в существующий файл.

Для каждого файла индекс хранит `id`, путь, размер, `mtime`, `revision` и хеш последнего принятого содержимого. Хеш считается по телу файла без YAML, чтобы служебные поля не создавали ложных изменений. Изменение считается внешним, если хеш отличается от известного, а операция не отмечена в журнале собственных записей приложения.

Кандидат наблюдателя — `watchdog` в Python-процессе; окончательный выбор и поведение на сетевых папках проверяются в E02. Резервный вариант — периодическая сверка без мгновенной реакции.

## Стабильность чтения

- Игнорируются временные, lock- и скрытые файлы: `.DS_Store`, `~$*`, `*.swp`, `*.tmp`, `*.crdownload`, `*.part`, содержимое `.system/`.
- События по одному пути объединяются. Файл читается после стабилизации размера и `mtime`; предлагается повторная проверка через 300–500 мс и предел ожидания около 2 секунд.
- Атомарное сохранение через временный файл и переименование (vim, VS Code, Obsidian) распознаётся как обновление, а не удаление с последующим созданием.
- Если файл занят или меняется во время чтения, чтение повторяется. После нескольких неудач показывается ошибка, автоматическая запись приложения не выполняется.
- При записи приложение сначала пишет временный файл, затем повторно проверяет хеш целевого файла и только после совпадения переименовывает его. Если файл изменился между проверкой и заменой, временный файл становится конфликтной версией, а файл человека остаётся на месте.
- Массовое изменение (sync-клиент, `git checkout`, восстановление из копии) и недоступность корня останавливают автоматическую запись до сверки. Приложение не создаёт папку заново и не очищает индекс по одному событию.

## Ревизии и служебные поля

- `id` в YAML — стабильный ключ; путь и имя файла не являются идентификатором.
- `revision` — последняя ревизия, известная приложению. Внешний редактор может её не менять, поэтому конфликт определяется по хешу, а не только по номеру.
- Приложение не переписывает тело изменённого человеком файла и не обязано править его YAML. Происхождение правки, время, ревизия и хеш записываются в боковой JSON и индекс.
- Последняя принятая версия каждой записи хранится в `.system/versions/<id>/<revision>-<timestamp>.md`; перед принятием внешней правки предыдущая версия фиксируется там же. Это позволяет показать исходное наблюдение и подтвердить сохранность доказательств.
- Правка текста не удаляет предыдущую версию. Чтобы стереть исходное содержимое, нужно удалить запись или версии через очистку; интерфейс объясняет разницу.
- Неизвестные поля YAML сохраняются; приложение не удаляет их при собственной записи.

## Конфликты

Конфликт фиксируется, если:

1. приложение собирается записать файл, а хеш на диске уже отличается от базового;
2. два файла претендуют на один `id`;
3. внешняя правка затронула файл, который приложение должно автоматически обновить (сводка дня `index.md`, карточка, производная запись);
4. файл изменён во время незавершённой операции записи.

Правило: файл по исходному пути сохраняет версию человека; версия приложения записывается рядом, в `conflicts/`, с суффиксом `.app-<timestamp>.md` и JSON-описанием. Обе версии индексируются, в интерфейсе показывается расхождение и путь к каждой. Автоматического слияния и выбора «правильной» версии нет. Копия в `conflicts/` помечается как конфликтный артефакт и не участвует в выборе канонического файла по `id`; иначе дубль `id` создал бы новый конфликт.

```text
days/2026/10/25/notes/
  15-10-00_note-abc.md                              — версия человека, остаётся на месте
  conflicts/
    15-10-00_note-abc.app-2026-10-25T15-12-00.md    — версия приложения
    15-10-00_note-abc.app-2026-10-25T15-12-00.json  — причина, ревизии, хеши
```

JSON конфликта содержит `conflict_id`, `entity_id`, `base_revision`, `base_hash`, `external_hash`, `app_revision`, `app_hash`, `created_at`, `reason` и `status`. Действия человека: открыть обе версии, оставить внешнюю, оставить версию приложения, сохранить обе как отдельные заметки, объединить вручную, отметить конфликт решённым. Замена файла версией приложения выполняется только после явного подтверждения; предыдущая версия при этом не теряется.

Для производных файлов (`index.md`, сводки, карточки) действует отдельное правило: если файл изменён человеком или помечен `user_edited`, автоматическая генерация пропускается, сводка помечается `stale`, а интерфейс предлагает пересчёт с предпросмотром. Пересчёт создаёт новую ревизию или конфликт, но не затирает ручной текст.

Для исходного контекста внешняя правка помечается как пользовательская: сохраняются `source_id`, ссылка на первоначальное наблюдение и исходная версия. Зависимые сводки помечаются устаревшими. В поиске и ответах такой текст обозначается как изменённый человеком и не выдаётся за первоначальное наблюдение.

## Переименование, перенос и удаление

- Если старый путь исчез, а файл с тем же `id` появился в другом месте в течение льготного времени (предлагается 5 секунд), это переименование или перенос: путь обновляется, ревизии и связи сохраняются.
- Файл без YAML в `notes/` импортируется как пользовательская заметка: приложение создаёт `id` и боковые метаданные, но не переписывает текст. Неизвестный Markdown в других папках, включая `tasks/`, показывается как «найден новый файл» и не становится заметкой и не отправляется модели без действия человека. Файлы `README.md` и `index.md`, содержимое `conflicts/` и `.system/`, скрытые, временные и вложения не импортируются как заметки без ссылки.
- Дублирующийся `id` — конфликт; приложение не угадывает, какой файл главный.
- Ошибочный YAML не удаляет файл. Тело индексируется с предупреждением «метаданные не разобраны», структурированные поля не считаются доверенными, ошибка видна в интерфейсе. После исправления файл переиндексируется.
- Внешнее удаление после льготного времени убирает запись из индекса и добавляет в `deletions.jsonl` отметку `id`/путь/хеш без содержимого. Очередь не восстанавливает удалённое. Связанные версии и конфликтные копии по умолчанию удаляются вместе с записью; если приложение работает и конфликт ещё не разрешён, он сначала показывается человеку. Если человек сознательно создаст файл снова, он будет проиндексирован как новое внешнее изменение; отметка запрещает автоматическую генерацию, а не осознанное восстановление.
- Если исчез весь корень или пропал доступ, приложение останавливает запись и показывает статус. Оно не восстанавливает папку из индекса; после возврата доступа выполняется сверка.

## Переиндексация

- Принятая правка обновляет путь, хеш и ревизию, заменяет фрагменты в FTS и векторном индексе, удаляет фрагменты старого тела и обновляет связи по `id`.
- Зависимые сводки и карточки помечаются устаревшими, а не пересчитываются молча. Пересчёт фиксирует, какую ревизию он использовал.
- Поиск не возвращает удалённый текст. Обе версии конфликта могут быть доступны, но с явной пометкой.
- Полная перестройка индекса из файлов должна воспроизводить текущее состояние; версии и конфликты читаются из папок, а не только из SQLite.

## Безопасность и ограничения

- YAML разбирается безопасно, без создания произвольных объектов; действуют ограничения размера и глубины.
- Markdown и HTML из файлов очищаются перед показом; внешние ссылки открываются только по действию человека; скрипты не исполняются.
- Символические ссылки не читаются за пределами корня памяти; обход путей отклоняется.
- Sync-клиенты могут создавать собственные конфликтные копии. Они импортируются или помечаются, но не перезаписываются молча; семантика слияния Dropbox, iCloud и OneDrive не обещается.
- Приложение не шифрует папку памяти. Защита диска и права доступа — ответственность пользователя; секреты API и OAuth в папке не хранятся.
- Наблюдение за сетевой папкой и съёмным носителем не гарантируется. Если оно не поддерживается, показывается предупреждение и используется сверка при запуске и вручную.

## Интерфейс

- Статус «внешние изменения обработаны» с временем и количеством; ошибки видны, но не блокируют чтение памяти.
- Список конфликтов: объект, время, причина, пути, сравнение версий и действия.
- «Открыть в редакторе по умолчанию», «Переиндексировать», «Показать исходную версию».
- Обычные внешние правки не вызывают модальных окон; подтверждение требуется только для конфликтов и разрушительных действий.
- Если приложение было закрыто, изменения подхватываются при следующем запуске; данные не теряются.

## Приёмка

| Проверка | Критерий |
| --- | --- |
| Правка заметки | Изменение в TextEdit, Notepad или Obsidian подхватывается; новый текст находится поиском, старые фрагменты исчезают |
| Правка контекста | Файл помечен как пользовательский, исходная версия доступна, зависимая сводка устарела, ответ помечает источник как изменённый |
| Конфликт | Внешняя правка и автоматическая запись не перезаписывают друг друга; обе версии существуют, файл человека остаётся на месте, конфликт виден |
| Атомарное сохранение | Сохранение через временный файл и переименование даёт одно обновление без дубля и ложного удаления |
| Переименование | Перенос внутри папки сохраняет `id` и связи; путь в индексе обновляется |
| Внешнее удаление | Запись исчезает из поиска после льготного времени и не возвращается из очереди после перезапуска |
| Неизвестный файл | Markdown без YAML в `notes/` импортируется как заметка без перезаписи текста; дубль `id` даёт конфликт |
| Ошибочный YAML | Файл сохранён, тело не потеряно, ошибка показана, после исправления поиск обновляется |
| Версии и очистка | Правка не удаляет исходную версию; удаление записи убирает связанные версии и конфликты из поиска и папок |
| Массовое изменение | Недоступность корня или массовая правка останавливают запись; после возврата доступа состояние сверяется |
| Работа без приложения | Правки, сделанные при закрытом приложении, подхватываются при запуске |
| Восстановление индекса | После удаления SQLite связи и записи восстанавливаются из файлов, версий и конфликтов |

## Открытые технические вопросы

- Наблюдатель: `watchdog`, `chokidar` или встроенные API; поведение на FSEvents, ReadDirectoryChangesW, сетевых папках и съёмных дисках.
- Задержки: стабильное чтение 300–500 мс, льготное время удаления около 2 секунд, переименования около 5 секунд, периодическая сверка около 5 минут. Значения требуют проверки.
- Расположение конфликтов: `conflicts/` рядом с исходной папкой или единый корень. Предлагается рядом.
- Нужен ли трёхсторонний merge в первой версии. Предлагается не обещать автоматическое слияние.
- Срок хранения версий и конфликтов: конфликты предлагается хранить до разрешения, версии — по настраиваемому сроку; числовые значения не выбраны.
- Показывать ли `.system/versions` в интерфейсе или дублировать в видимую папку истории.

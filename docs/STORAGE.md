# Открытое файловое хранилище

Статус: согласованы Markdown/JSON с вложениями по датам, SQLite для индекса и служебного состояния, просмотр и редактирование сторонними программами. Детали реализации и проверки ниже — технический контракт, ещё не реализованный. Подхват внешних правок, ревизии и конфликты подробно описаны в [EXTERNAL_EDITS.md](EXTERNAL_EDITS.md).

## Требование

Все заметки и сохранённый контекст должны быть доступны как обычные файлы, которые человек может просматривать без нашего приложения. Организация по датам предпочтительна. Это постоянное представление памяти, а не необязательная выгрузка по кнопке. Сохраняется только собранный разрешённый контекст; срок хранения снимков и журнала отправок по-прежнему ограничивается настройками.

## Предлагаемая структура

```text
Memory/
  README.md
  days/
    2026/
      10/
        25/
          index.md
          episodes/
            14-32-10_ep-<id>.md
          context/
            14-32-10_obs-<id>.md
          notes/
            15-10-00_note-<id>.md
          sources/
            obs-<id>.json
          requests/
            req-<id>.json
          attachments/
            shot-<id>.png
          conflicts/
            15-10-00_note-<id>.app-2026-10-25T15-12-00.md
            15-10-00_note-<id>.app-2026-10-25T15-12-00.json
  tasks/
    task-<id>.md
    conflicts/
  .system/
    manifest.json
    deletions.jsonl
    versions/
      <id>/
        0001-2026-10-25T14-32-10.md
    runtime.sqlite
```

Имена файлов содержат время и стабильный идентификатор; пользовательский заголовок находится внутри файла. Это предотвращает конфликты одинаковых названий и недопустимые символы Windows. Дата папки определяется часовым поясом хранилища на момент создания записи; смена часового пояса не перемещает старые файлы. Импорт прошлой истории раскладывается по дате посещения, импортированная заметка без достоверной даты события — по дате импорта. Обе временные отметки сохраняются.

Папки `days` и `tasks` — человекочитаемая память; `.system` содержит служебные версии, журнал удалений и индекс и не требуется для чтения. `conflicts` хранит расходящиеся версии, чтобы человек мог их сравнить.

## Что хранится

| Представление | Формат | Содержимое |
| --- | --- | --- |
| Оглавление дня | Markdown | Эпизоды, заметки, задачи, приложения, ссылки на подробности |
| Эпизод | Markdown | Краткое описание, наблюдавшиеся действия, интервалы, гипотезы отдельно от фактов, источники |
| Полный сохранённый текст | Markdown | Полученный текст страницы, OCR, документа или заметки; не только пересказ модели |
| Пользовательская заметка | Markdown | Текст и ссылки, которые пользователь сохранил или написал |
| Задача | Markdown | Состояние, срок, подтверждение, источники; располагается отдельно, потому что живёт несколько дней |
| Метаданные источника | JSON | Тип, URL/путь, время, версия, координаты OCR, метод извлечения; связаны по id с Markdown |
| Запрос модели | JSON | Фактически отправленный контент или ссылки на файлы, режим, назначение, статус; без настроенных токенов авторизации |
| Изображение | PNG/JPEG | Отдельный файл; до последнего этапа без маскировки |
| Предыдущая версия | Markdown/JSON | Содержимое до принятой внешней правки; хранится в `.system/versions` для сохранности доказательств |
| Конфликтная версия | Markdown/JSON | Версия приложения рядом с версией человека и описание причины, ревизий и хешей |
| Поисковый индекс | SQLite | Производные данные для быстрого поиска; пользователь не обязан открывать базу |

В начало Markdown предлагается добавлять короткие служебные поля YAML: schema_version, id, kind, created_at, observed_at, timezone, source_ids, privacy_mode и revision. Они читаемы и позволяют восстановить индекс. Ссылки между файлами относительные, внутри приложения сущности также связываются по id. Внешние ссылки на сайты не заменяют сохранённый контент: страница может измениться.

## Источник истины и восстановление

Markdown, JSON и вложения — источник истины для долговременной памяти. SQLite содержит восстанавливаемый поисковый индекс и отдельное служебное состояние очередей, синхронизации и настроек. Восстановление индекса не обещает восстановить незавершённую отправку API или OAuth-сессию. Секреты остаются в системном хранилище, не в папке памяти.

Приложение пишет файлы автоматически. Один координатор записи сначала сохраняет временный файл и атомарно заменяет целевой, затем обновляет индекс. Для нескольких связанных файлов используется журнал операции и отметка завершения в manifest. После сбоя незавершённая операция завершается либо откатывается до целого набора; индекс сверяется по id, revision и хешу содержимого. Сводка дня является производной и может быть построена заново.

Записи, требующие локального обезличивания, проходят его до создания соответствующей очищенной версии. Режим без маскировки сохраняет исходный разрешённый контент. Автоматическое преобразование не должно незаметно менять режим старых записей.

## Изменения человеком

Просмотр и редактирование файлов сторонними программами подтверждены пользователем. Приложение отслеживает изменения, сверяет хеши, обновляет индекс и не перезаписывает пользовательский текст. При конфликте ревизий сохраняются обе версии, конфликт показывается человеку. Ошибочный YAML не удаляет файл, а помечается как ошибка индексации. Полный контракт, сценарии и приёмка: [внешние правки и конфликты](EXTERNAL_EDITS.md).

Исходный собранный контекст считается доказательством: изменения такого файла фиксируются как пользовательская правка, а не продолжают представляться первоначальным наблюдением; предыдущая версия сохраняется. Неизвестный новый файл не даёт разрешения отправить его модели автоматически: сначала он должен соответствовать выбранным правилам источников. Чтение папки в Obsidian не требует отдельной интеграции с Obsidian.

Кратко о механике: наблюдатель файлов и сверка хешей при запуске и возвращении доступа; атомарное сохранение редактора распознаётся как обновление, а не удаление; стабильный `id` сохраняет связи при переименовании; правка старого контекста обновляет поиск и помечает связанные сводки как требующие пересчёта; автоматическая генерация не затирает ручные изменения.

## Удаление и ограничения

Удаление через приложение распространяется на Markdown, JSON, изображения, сводки, производные индексы и копии в журнале. Метка удаления не содержит исходного текста и предотвращает восстановление удалённого из очереди. Внешнее удаление файла также удаляет запись из поиска и связанные версии, если нет открытого конфликта; приложение не создаёт её обратно из старого индекса. Удаление папки в работающем приложении обнаруживается как потеря доступа/массовое изменение и останавливает запись до проверки состояния.

Очистка снимков удаляет изображения и все их дополнительные копии, в том числе встроенные данные запроса, если они сохранялись. В Markdown остаётся отметка «снимок удалён по сроку хранения», а не неработающая ссылка. Текстовая память и заметки не удаляются вместе со снимком. Удаление локальной папки не удаляет пользовательские резервные копии или уже отправленные данные у поставщика модели.

Файловая папка может занимать больше места, чем сжатый внутренний формат, поэтому сохраняются изменения, а не одинаковый текст каждый цикл. Версии и конфликтные копии тоже занимают место; предлагается ограничивать их количество или срок, а конфликты хранить до разрешения человеком. Полные URL и контент могут содержать персональные данные; настройка режимов сохраняется. Размещение папки в синхронизируемой облачной директории означает передачу файлов её клиентом; приложение по умолчанию предлагает локальную папку без собственного облачного обмена.

## Приёмка файлового хранилища

1. Без запуска приложения открыть папку дня и прочитать эпизод, полный сохранённый контекст, заметки и ссылки.
2. На копии хранилища удалить только производный индекс и восстановить поиск и связи из файлов без обращения к модели.
3. Проверить дату импорта и дату события, одинаковое время записей, кириллицу, перенос папки на другой путь и доступность относительных ссылок.
4. Остановить процесс между записью файлов и индекса, затем восстановить согласованное состояние без дублирования.
5. Удалить эпизод и снимки; убедиться, что они не возвращаются из индекса или очереди.
6. Изменить заметку при работающем приложении и при закрытом; поиск обновляется, старые фрагменты не находятся.
7. Смоделировать конфликт внешней правки и автоматической записи; файл человека не перезаписан, обе версии сохранены и видны.
8. Переименовать файл, сломать YAML и удалить файл внешне; связи сохраняются, ошибка не удаляет текст, удалённое не возвращается.
9. Полный набор проверок внешних правок — в [приёмке контракта](EXTERNAL_EDITS.md#приёмка).

# Регламент разработки с Antigravity

Начать с [MILESTONES](MILESTONES.md), затем [REVIEW](REVIEW.md), [BACKLOG](BACKLOG.md), [TESTING](TESTING.md). Текущий статус: реализация M1 и облачные проверки завершены; следующий обязательный этап — SB-14 на реальном Mac, затем исправление только обнаруженных дефектов. Прочитать [итоговый отчёт](reports/2026-10-25-M1-implementation.md). Не начинать реализованные карточки заново.

## Правила работы

1. Взять первую TODO с выполненными зависимостями; выставить IN_PROGRESS с датой и исполнителем. Не делать несколько несвязанных карточек за один проход.
2. Прочитать актуальные инструкции репозитория и git status. Сохранить пользовательские изменения; работать в существующем checkout. Облачная задача уже изолирована: worktree создавать только по явной просьбе пользователя.
3. Воспроизвести дефект или зафиксировать недостающее поведение. До исправления записать failing check; по возможности автоматизировать сценарий.
4. Изменить минимальный необходимый объём. Сначала контракт/ядро, затем UI. Не менять макеты, зависимости и архитектуру заодно без нужды карточки. Не удалять старые экраны только потому, что они кажутся неиспользуемыми: сначала проверить импорты и сценарии.
5. Выполнить проверки карточки и общий verify. Само наличие кнопки, успешная сборка, скриншот или mock не доказывают сохранение на диск, перезапуск и native bridge.
6. Самостоятельно ревью diff: ошибки/конфликты, повторный submit, stale response, блокировка main thread, сохранность файлов, секреты, корректность сортировки и доступность управления.
7. Создать отчёт по TESTING. Только после доказательств перевести в DONE. При внешней зависимости — BLOCKED с точной причиной и последней диагностикой; не подменять живую интеграцию симуляцией.
8. Обновить ссылки на тесты/отчёт в карточке. Коммит/push/PR выполняются по отдельной авторизации пользователя. Перед следующей задачей проверить зависимости; не переписывать историю статусов.

## Критерии ревью любой задачи

- Данные поступают из реального transport; demo включается явно и заметно.
- Повтор операции и restart не создают дубликаты и не теряют изменения.
- UI различает loading/empty/error/conflict/success; ввод не пропадает при сбое.
- Любой видимый элемент управления имеет поведение и проверку; незавершённая интеграция явно обозначена.
- Ключи и содержимое документов не попали в логи/fixtures; stdout Python остаётся JSON.
- Сортировка проверена на равенствах, пустых значениях, кириллице и нескольких страницах.
- Выполненные и невыполненные проверки перечислены честно. DONE относится к доказанному поведению, а не к объёму написанного кода.

## Границы среды

В текущей облачной Linux-машине доступны Python suite, сборка, typecheck, backend subprocess и HTTP-проверки Vite. Она не доказывает работу macOS Keychain, native OCR, разрешений или меню/трея. Для GUI использовать доступный browser MCP; при его отсутствии явно писать UNRUN и использовать отдельный поддерживаемый test runner после SB-13. Не подключать общий пользовательский Chrome и не выдавать localhost-ссылки за облачный preview.

Внешние LLM/NeuralDeep проверять только по явному opt-in, с тестовыми неперсональными данными и credentials через безопасные настройки. Не просить значения ключей в чате. Отсутствие live credentials не мешает локальным M1 unit/contract tests, но не закрывает M2 live acceptance.
